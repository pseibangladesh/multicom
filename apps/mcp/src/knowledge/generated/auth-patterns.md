## Authentication Patterns

Bengali Exchange uses **Better Auth** for people (email + password, with email verification) and API keys / OAuth tokens for machines. There is no external identity provider.

### Where it runs

- `apps/merchant/src/lib/auth.ts` builds `betterAuth` with the Drizzle adapter over the `MerchantDO` SQLite storage. It runs **inside the Durable Object**; the Worker forwards `/api/auth/*` to it.
- The session is an **HttpOnly cookie**. The client never holds a token.
- The Worker verifies a session by asking the DO (`src/lib/session.ts`).

### Email verification

- `requireEmailVerification: true`: a new account cannot sign in until it confirms its address.
- `POST /api/auth/sign-up/email` creates the user and emails a confirmation link (`lib/auth-email.ts` → Mailgun). **No session is created.**
- `GET /api/auth/verify-email?token=…&callbackURL=…` marks the email verified and signs the user in.
- `POST /api/auth/sign-in/email` for an unverified user returns **403** with code `EMAIL_NOT_VERIFIED` and sends a fresh link.
- `POST /api/auth/send-verification-email { email, callbackURL }` re-sends the link.
- Without Mailgun configured, the link is printed with `console.warn` (development only — production needs `MAILGUN_API_KEY` / `MAILGUN_DOMAIN`).

### Who is an admin

Admins are the users whose email is listed in the `ADMIN_EMAILS` env var. They are marked verified automatically, so they can't be locked out. Everyone else is a customer.

### Credentials accepted by `authMiddleware`

Checked in this order (`apps/merchant/src/middleware/auth.ts`):

1. **Better Auth session cookie**: role `admin` for ADMIN_EMAILS, otherwise rejected on admin routes.
2. **OAuth token** (64-char hex): role `oauth`, with scopes.
3. **API key**: `sk_` (admin) or `pk_` (public storefront), SHA-256 hashed in `api_keys`.

### Roles

| Role | Assigned to |
|---|---|
| `public` | storefront `pk_` key |
| `admin` | `sk_` key, or a session whose email is in ADMIN_EMAILS |
| `oauth` | OAuth token (AI agents) |
| `customer` | a verified customer session (`customerAuthMiddleware`) |

### Guards

| Guard | Checks | Use |
|---|---|---|
| `adminOnly` | role is `admin` | every admin route (catalogue, orders, setup and migrations, mail, AI settings) |
| `requireScope(...scopes)` | OAuth token scopes | OAuth-scoped routes |
| `customerAuthMiddleware` | verified Better Auth session | `/v1/me/*` and other customer routes |

```ts
const route = createRoute({
  method: 'get',
  path: '/v1/admin/things',
  middleware: [authMiddleware, adminOnly] as const,
  // ...
});
```

### Customer routes

`customerAuthMiddleware` rejects API keys, requires a verified session (403 "Please verify your email address first" otherwise) and sets `auth.userId`. Always derive the customer from it:

```ts
const auth = c.get('auth');
const customer = await resolveCustomer(db, auth.userId!); // lib/customers.ts
```

`resolveCustomer` maps the Better Auth user to a `customers` row (claiming an existing row with the same email, or creating one) and links earlier guest orders placed with that email. Never accept a customer id or email from the request body.

### Frontend

- `AuthenticationGuard` (prop `component`) sends signed-out visitors to `/login?returnTo=…`.
- `AdminGuard` wraps `/admin`; only sessions with `user.is_admin` get in.
- `useAuth()` gives `isAuthenticated`, `isLoading`, `user`, `isAdmin`, `signInEmail`, `signUpEmail`, `resendVerification`, `logout`.
- `isAdmin` is a UI hint only (hide admin-only buttons); the API enforces access itself.
- `EmailAuthForm` (`features/auth/components/email-auth-form.tsx`) is the sign-in / create-account form used by `/login` and `LoginModal`. After sign-up it shows a "check your email" step with a resend button; an `EmailNotVerifiedError` on sign-in shows the same step.
