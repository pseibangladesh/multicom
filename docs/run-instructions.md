# Multicom — Run Instructions (Fresh Clone)

**For setting up a new machine from scratch after `git clone`.**

---

## Prerequisites

| Tool | Minimum Version | Purpose |
|------|----------------|---------|
| [Node.js](https://nodejs.org/) | 20.x LTS | Runtime for all tooling |
| [npm](https://www.npmjs.com/) | 11.14.1+ (see `packageManager` in root `package.json`) | Package manager / monorepo orchestrator |
| [Wrangler CLI](https://developers.cloudflare.com/workers/wrangler/) | 4.x | Cloudflare Workers local dev + deployment |
| [Stripe CLI](https://stripe.com/docs/stripe-cli) (optional) | Latest | Forward Stripe webhooks to localhost |

Install Node.js and npm first:

```bash
# Using nvm (recommended)
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.3/install.sh | bash
nvm install 20
nvm use 20

# Verify
node -v   # v20.x
npm -v    # 11.x+
```

Install Wrangler globally:

```bash
npm install -g wrangler
wrangler --version   # verify installation
```

## 1. Clone and Install

```bash
# Clone the repository
git clone https://github.com/<your-org>/multicom.git
cd multicom

# Install all workspace dependencies (root installs everything)
npm install
```

This bootstraps every workspace under `apps/`:
- `apps/merchant` — Cloudflare Worker backend
- `apps/client` — React storefront + admin SPA
- `apps/merchant/admin` — Admin panel (separate Vite app inside merchant)
- `apps/mcp` — MCP knowledge server

## 2. Environment Configuration

The project has **no `.env.example` files committed** (sensitive values are excluded from git). You must create them manually.

### 2.1 Backend `.env` (monorepo root)

Create `/multicom/.env` at the **monorepo root**. The merchant worker does not read `.env` itself: Wrangler reads `apps/merchant/.dev.vars`. `npm run dev:env` (via `apps/merchant/dev-env.sh`) copies `.env` over `.dev.vars` on every start; plain `npm run dev` does not, so after editing `.env` either use `dev:env` or update `.dev.vars` too.

```bash
# === REQUIRED: API Keys ===
MERCHANT_SK=sk_your_64_hex_chars_here          # Admin API key (generated by init script)
MERCHANT_PK=pk_your_64_hex_chars_here          # Public API key (generated by init script)

# === REQUIRED: Better Auth ===
BETTER_AUTH_SECRET=your_32_char_random_string_here   # Signs session cookies
ADMIN_EMAILS=you@example.com                   # Comma-separated; only these sessions get admin. Create their logins with create-admin.ts (3.2); public sign-up refuses these addresses
API_BASE_URL=http://localhost:8787             # Worker URL for cookie callbacks

# === REQUIRED: Storage & Caching ===
CRYPTOKEN=your_32_char_hex_string_here               # AES-GCM encryption for secrets at rest
ORDER_TOKEN_SECRET=your_32_char_random_string_here   # HMAC secret for order view tokens

# === REQUIRED (production): Stripe ===
STRIPE_SECRET_KEY=sk_live_your_stripe_key_here
STRIPE_PUBLISHABLE_KEY=pk_live_your_publishable_key_here
STRIPE_WEBHOOK_SECRET=whsec_your_webhook_secret_here

# === OPTIONAL: Email (Mailgun) ===
MAILGUN_USER=your_mailgun_user_here
MAILGUN_API_KEY=your_mailgun_api_key_here
MAILGUN_DOMAIN=your_mailgun_domain_here
MAILGUN_BASE_URL=https://api.mailgun.net

# === OPTIONAL: AI Translation ===
AI_API_KEY=your_groq_or_openai_api_key_here
AI_MODEL=llama-3.3-70b-versatile
AI_API_URL=https://api.groq.com/openai/v1

# === OPTIONAL: Store Identity ===
STORE_NAME="My Store"
STORE_URL=http://localhost:5173

# === OPTIONAL: Cloudflare AI Gateway ===
CLOUDFLARE_AIG_TOKEN=your_cf_aig_token_here
DISABLE_CLOUDFLARE_AIG=false

# === OPTIONAL: Cache TTL overrides (defaults in brackets) ===
KV_CACHE_SEARCH_TTL_SECONDS=300
KV_CACHE_REVIEWS_TTL_SECONDS=600
KV_CACHE_DEFAULT_TTL_SECONDS=3600

# === CORS & Frontend ===
CORS_ORIGIN=http://localhost:5173

# === Marketplace (see Section 4 below) ===
# ETSY_CLIENT_ID=...
# ETSY_SHARED_SECRET=...
# EBAY_CLIENT_ID=...
# EBAY_CLIENT_SECRET=...
# EBAY_RU_NAME=...
# AMAZON_SP_APP_ID=...
# AMAZON_LWA_CLIENT_ID=...
# AMAZON_LWA_CLIENT_SECRET=...
# AMAZON_REGION=NA
```

> **⚠️ Security**: Never commit `.env` to git. It is listed in `.gitignore`.

## 3. Backend Setup & Local Development

### 3.1 Initialize Database and API Keys

```bash
# From monorepo root, run the init script:
npx tsx apps/merchant/scripts/init.ts
```

This does three things:
1. Starts the Worker locally (if not already running) and creates the Durable Object schema
2. Generates or reuses `MERCHANT_SK` and `MERCHANT_PK` from your `.env`
3. Seeds base currencies and countries into the SQLite database

It prints the generated API keys — **save these**. If you already have keys in `.env`, it reuses them instead of generating new ones.

For remote (production) initialization:

```bash
API_BASE_URL=https://your-worker.workers.dev npx tsx apps/merchant/scripts/init.ts --remote
```

Re-running it is safe: existing API keys (409) and existing currencies/countries are reused.

### 3.2 Set Up the Super Admin and Log In

Admins are created with a script, never through the storefront sign-up form (that form refuses any address listed in `ADMIN_EMAILS`). Four steps:

**Step 1. Choose the admin email.** Put it in `ADMIN_EMAILS` in the root `.env` (comma-separated for more than one):

```bash
ADMIN_EMAILS=you@example.com
```

**Step 2. Start (or restart) the backend with that setting.** The local worker reads `apps/merchant/.dev.vars`, not `.env`. `npm run dev:env` copies `.env` into it for you:

```bash
npm run dev:env
```

(If you use plain `npm run dev`, add the same `ADMIN_EMAILS=...` line to `apps/merchant/.dev.vars` yourself, then restart.)

**Step 3. Create the admin's login.** In a second terminal, from the monorepo root:

```bash
npx tsx apps/merchant/scripts/create-admin.ts you@example.com
```

It asks for the password twice (8+ characters, not shown while typing). You can also pass it directly: `create-admin.ts you@example.com 'your-password' --name "Your Name"`.

Check the last lines of the output:
- `✅ Account created` and `✅ The backend recognises this email as an admin`: you're done.
- `⚠️ The backend does NOT treat this email as an admin yet`: the worker didn't get `ADMIN_EMAILS`. Redo step 2, then sign in again (no need to rerun the script).
- `This account already exists; password left unchanged`: the email was registered before (for example through the storefront). Set the password you want with `--reset-password`.

**Step 4. Log in to the admin dashboard.**
1. Open `http://localhost:5173/login`.
2. Sign in with the email from step 1 and the password you typed in step 3.
3. Open `http://localhost:5173/admin`.

If you were already signed in before restarting the worker, sign out and back in first.

| Problem | Fix |
|---|---|
| Forgot the password | `npx tsx apps/merchant/scripts/create-admin.ts you@example.com --reset-password` |
| Logged in but no admin dashboard | Email missing from `ADMIN_EMAILS` in `apps/merchant/.dev.vars`; fix it, restart, sign in again |
| `The backend rejected MERCHANT_SK` | `MERCHANT_SK` in `.env` differs from the key the worker uses; rerun `init.ts` (3.1) and restart |
| `Cannot reach http://localhost:8787` | The backend isn't running; do step 2 |

Note: the demo seed (3.3) does not create an admin account; seeded customers are storefront users only. Use this script for admins.

**Deployed worker** (the password is only ever sent over https):

```bash
cd apps/merchant && npx wrangler secret put ADMIN_EMAILS && cd ../..
npx tsx apps/merchant/scripts/create-admin.ts you@example.com --remote   # uses API_BASE_URL from .env
```

How it works: the script calls `POST /v1/setup/admin-user` with `MERCHANT_SK`. The Durable Object writes the Better Auth `user` and credential `account` rows with Better Auth's own password hasher, the same rows a normal sign-up creates, so the regular login form accepts them.

### 3.3 Seed Demo Data (Optional)

```bash
# From monorepo root:
npx tsx apps/merchant/scripts/seed.ts http://localhost:8787 <MERCHANT_SK>

# Wipe the demo data and seed again from scratch (local worker only):
npx tsx apps/merchant/scripts/seed.ts http://localhost:8787 <MERCHANT_SK> --force
```

This populates the database with sample regions, tax rates, products, and orders for testing. It is safe to re-run: records are matched by handle, SKU, name or customer email and only missing ones are created, and stock is never added twice. `--force` keeps currencies, countries, API keys, settings and user accounts.

With the 100 requests/minute limit for keys that don't start with `sk_`, a full seed takes about 5 minutes; the script waits out rate limits on its own.

### 3.4 Start the Backend

```bash
# From monorepo root (recommended — loads .env automatically):
npm run dev:env

# Or from the merchant workspace directly:
cd apps/merchant && npm run dev
```

The Worker starts at **`http://localhost:8787`**. `npm run dev:env` runs `dev-env.sh`, which copies `.env` to `.dev.vars` (Wrangler's local secrets file) and starts `wrangler dev`. `npm run dev` uses `.dev.vars` as it is.

### 3.5 Stripe Webhook Forwarding (Optional)

```bash
# From monorepo root:
npm run stripe:listen
```

Requires the Stripe CLI installed. Reads `STRIPE_SECRET_KEY` from `.env` and forwards Stripe webhook events to `localhost:8787`.

### 3.6 Frontend Development

```bash
# From monorepo root (recommended — loads .env automatically):
npm run dev:env

# Or start just the client:
cd apps/client && npm run dev
```

The Vite SPA starts at **`http://localhost:5173`**. It connects to the backend at `API_BASE_URL`.

| Service | URL | Port |
|---------|-----|------|
| Backend (Worker) | `http://localhost:8787` | 8787 |

| OpenAPI/Swagger UI | `http://localhost:8787/docs` | — |
| Stripe webhook forwarder | `localhost:4242` → `localhost:8787` | 4242 |

Subpath mounting (optional):

```bash
npm run dev:env -- --base=/multicom
# → Frontend: http://localhost:5173/multicom
# → Worker .dev.vars: STORE_URL and CORS_ORIGIN auto-adjusted
```

## 4. External API Key Setup

### 4.1 Better Auth (Built-in)

No external setup required. Better Auth is bundled in the worker and uses the `BETTER_AUTH_SECRET` environment variable.

**To set a strong secret:**

```bash
# Generate a random 64-char secret:
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Add it to your `.env`:
```
BETTER_AUTH_SECRET=paste_the_generated_secret_here
```

**Sign-up / Sign-in:**
- `POST /api/auth/signup/email` — `{ email, password }`
- `POST /api/auth/signin/email` — `{ email, password }`
- `POST /api/auth/signout` — invalidates the current session
- `GET /api/auth/session` — returns current session data (used by frontend)

The backend issues a secure HttpOnly cookie (`better-auth.session_token`) containing a random token. The raw token is hashed with SHA-256 and stored in the D1 `sessions` table.

### 4.2 Stripe

1. Create a [Stripe account](https://dashboard.stripe.com/)
2. Get your API keys from **Developers → API keys**:
   - `sk_live_...` (Secret Key) — for the backend
   - `pk_live_...` (Publishable Key) — for the frontend checkout
3. Set up a [Webhook Endpoint](https://dashboard.stripe.com/webhooks):
   - Endpoint URL: `https://your-worker.workers.dev/v1/webhooks/stripe`
   - Listen for events: `checkout.session.completed`, `invoice.payment_succeeded`, etc.
   - Copy the **Webhook Secret** (`whsec_...`) to `.env`

For local development, use the Stripe CLI to forward webhooks:

```bash
stripe listen --forward-to localhost:8787
# Copy the generated webhook secret to STRIPE_WEBHOOK_SECRET in .env
```

**Turn Stripe on and enter the keys (recommended): Admin → Payment Gateways.** Sign in as an admin, open `/admin/payment-gateways`, and in the **Stripe** card:
1. Switch **Enabled** on.
2. Paste the **Publishable Key**, **Secret Key** and **Webhook Signing Secret**. The secret key is checked with Stripe before it is saved; secrets are stored encrypted with `CRYPTOKEN` and never shown again (only the last 4 characters).
3. Press **Save Settings**. The card shows **Test mode / Live mode**, whether Stripe is **Active at checkout**, and the webhook URL to add in the Stripe dashboard.

Leave a secret field blank to keep the current value. Switching Stripe off hides it from the storefront checkout; refunds and webhooks for existing orders keep working. The storefront only lists the gateways that are switched on (`GET /v1/payment-methods`).

Where the keys come from, highest priority first: keys saved on that page → `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` in the environment → the older setup API below. The card shows which one is in use.

Older alternative, by API:

```bash
curl -X POST http://localhost:8787/v1/setup/stripe \
  -H "Authorization: Bearer sk_<your-admin-key>" \
  -H "Content-Type: application/json" \
  -d '{"stripe_secret_key":"sk_live_...","stripe_webhook_secret":"whsec_..."}'
```

### 4.3 Mailgun (Transactional Email)

1. Create a [Mailgun account](https://www.mailgun.com/)
2. Get your API key from **Settings → API**
3. Verify your sending domain in Mailgun dashboard
4. Add to `.env`:


### 4.4 Etsy Marketplace Integration

1. Go to [Etsy Developers](https://www.etsy.com/developers/)
2. Create a new app → get your credentials
3. Add to `.env`:

```
ETSY_CLIENT_ID=your_app_keystring_here
ETSY_SHARED_SECRET=your_shared_secret_here
```

**OAuth Connect Flow:**
```
POST /v1/marketplace/connect/etsy   →  { channelId, authUrl }
GET  /v1/marketplace/connect/etsy/callback?code=...  →  exchanges code for tokens, stores encrypted credentials
```

Etsy uses OAuth 2.0 with the `keystring:shared_secret` API key header pattern.

### 4.5 eBay Marketplace Integration

1. Go to [eBay Developer Portal](https://developer.ebay.com/)
2. Create a new app → get OAuth credentials
3. Add to `.env`:

```
EBAY_CLIENT_ID=your_client_id_here
EBAY_CLIENT_SECRET=your_client_secret_here
EBAY_RU_NAME=your_ru_name_redirect_uri_alias_here
```

**OAuth Connect Flow:**
```
POST /v1/marketplace/connect/ebay   →  { channelId, authUrl }
GET  /v1/marketplace/connect/ebay/callback?code=...  →  exchanges code for tokens
```

eBay uses OAuth 2.0 with a RuName (redirect URI name) instead of a full URL.

### 4.6 Amazon SP-API Integration

Amazon is pull-based: orders are fetched every 15 minutes (and with **Pull orders**), and price/stock changes are pushed with **Push products**. No AWS keys are needed (Amazon dropped SigV4 signing in 2023); every call uses a Login with Amazon (LWA) access token.

**1. Register the app (one time, in Seller Central → Partner Network → Develop Apps)**

1. Create a developer profile (private developer is enough for your own store) and wait for approval.
2. Add a new app client. Choose the **SP API** type and these roles: *Product Listing*, *Inventory and Order Tracking*, *Pricing*. Add *Direct-to-Consumer Shipping* (restricted) only if you want buyer names, emails and addresses on imported orders.
3. In the app's OAuth settings, register:
   - **OAuth Login URI:** `https://<your-api>/v1/marketplace/connect/amazon/login`
   - **OAuth Redirect URI:** `https://<your-api>/v1/marketplace/connect/amazon/callback`

   For local development use `http://localhost:8787` (Amazon accepts it only while the app is in draft).
4. Copy the **app ID** (`amzn1.sp.solution…`) and the **LWA client ID and secret** (`amzn1.application-oa2-client…`).

**2. Add to `.env`**

```
AMAZON_SP_APP_ID=amzn1.sp.solution.xxxxxxxx
AMAZON_LWA_CLIENT_ID=amzn1.application-oa2-client.xxxxxxxx
AMAZON_LWA_CLIENT_SECRET=xxxxxxxx
AMAZON_REGION=NA              # NA | EU | FE
# Optional:
# AMAZON_MARKETPLACE_ID=ATVPDKIKX0DER   # default for the region (US / UK / JP)
# AMAZON_APP_DRAFT=true                 # while the app is unpublished (adds version=beta)
# AMAZON_ENVIRONMENT=sandbox            # SP-API sandbox endpoints
# AMAZON_SELLER_CENTRAL_URL=https://sellercentral.amazon.ca
# AMAZON_REDIRECT_URI=...               # default: API_BASE_URL + /v1/marketplace/connect/amazon/callback
```

The older names `AMAZON_LWA_APP_ID` / `AMAZON_LWA_APP_SECRET` still work. In production set them with `npx wrangler secret put`.

**3. Connect from the dashboard**

Open **Admin → Marketplaces → Connect new → Amazon**. Seller Central asks you to authorize the app, then returns to the callback, which stores the tokens (encrypted with `CRYPTOKEN`), records your seller ID and picks your marketplace.

```
POST /v1/marketplace/connect/amazon        →  { authUrl, state }
GET  /v1/marketplace/connect/amazon/login  →  302 back to Seller Central (Login URI step)
GET  /v1/marketplace/connect/amazon/callback?spapi_oauth_code=…&state=…&selling_partner_id=…
```

**4. Settings (Edit config)**

| Field | Used for |
|---|---|
| Marketplace ID | Which Amazon site to sell on. Set at connect time; prices must be in that site's currency. |
| Default carrier | Carrier sent with tracking numbers (`UPS`, `USPS`, `FedEx`, `DHL`…; other names go as `Other`). |
| Product type, brand, condition, language | Only for products **not yet on Amazon**. A variant whose barcode (UPC/EAN/GTIN) is in Amazon's catalog is offered on the existing product without them. |
| FBA orders | Off by default: only orders you ship yourself (MFN) are imported. |

**Good to know**

- Brand-new Amazon products often need extra, category-specific attributes. If Amazon rejects a listing, its reasons appear in the channel's last-job error; create the product in Seller Central once and later pushes will update its price and stock.
- Without the restricted role, orders still import, with a placeholder email and no street address.
- Stock is pushed as merchant-fulfilled quantity; FBA stock is managed by Amazon.

## 5. Cloudflare Bindings (Local Development)

The `wrangler.jsonc` declares the following bindings:

| Binding | Type | Local Dev Behavior |
|---------|------|-------------------|
| `MERCHANT` | Durable Object | Auto-provisioned SQLite in `.wrangler` |
| `IMAGES` | R2 Bucket | Virtual bucket in local emulation |
| `DIGITAL_ASSETS_BUCKET` | R2 Bucket | Virtual bucket in local emulation |

No remote Cloudflare resources are needed for local development. The Worker auto-creates the Durable Object schema via migrations on first startup.

## 6. Troubleshooting

### `Could not resolve "better-auth"` or other import errors

Run `npm install` from the **monorepo root** — workspace dependencies are hoisted. Do not run `npm install` inside individual workspaces.

### `wrangler: command not found`

Install Wrangler globally:
```bash
npm install -g wrangler
```

### Durable Object migration errors on first run

The migration is applied automatically via `ensureInitialized()` in `do.ts`. If the schema fails to create:
```bash
# Reset local state
rm -rf apps/merchant/.wrangler
cd apps/merchant && npm run dev
```

### CORS errors from frontend → backend

Ensure `CORS_ORIGIN=http://localhost:5173` is set in `.env`. The `dev-env.sh` script copies `.env` to `.dev.vars` which Wrangler uses as local secrets.

### "Missing or invalid session" on customer routes

Verify that the Better Auth session cookie is being sent with requests. The frontend's `useLocalProvider` uses `credentials: "include"` on all fetch calls, so this should work automatically for same-origin requests. If cross-origin, ensure `CORS_ORIGIN` matches the origin making the request.

### Port conflicts

The Worker uses port **8787** and Vite uses **5173**. If these are in use:
```bash
# Change Worker port in wrangler.jsonc:
# "dev": { "port": 8788 }

# Change Vite port in apps/client/vite.config.ts or:
cd apps/client && npx vite --port 3000
```
